- COD fee 3.33% is buyer-paid (DEC-009); Mengantar collects COD on 99ribu's account and finance reconciles each Mengantar COD settlement statement manually (DEC-007), with no seller payable.
- Delivery tracking: until S98 the simulated adapter (local) and the audited operator fallback are the delivery source.

Production auth gates (open; local loopback profile only):

- 2FA brute-force budget: TOTP and backup-code verification are each budgeted `5/min` per account, keyed on the HMAC of the user id resolved from Better Auth's pending `two_factor` verification row (`src/modules/access/handler.ts`), so fresh sign-ins no longer reset it; unresolvable cookies share one conservative bucket. Residual: an attacker holding the password still gets up to `5` TOTP plus `5` backup-code guesses per minute per account, bounded further only by Better Auth's default two-factor account lockout (`10` consecutive failures -> `900s`, not separately load-tested here). Review these numbers against load evidence before exposure.
- Client IP: the sign-in ceiling (`300/min`, `src/modules/access/auth.ts`) and guest bootstrap ceiling (`600/min`, `src/modules/checkout/access.ts`) are global buckets because every request is stamped `127.0.0.1`. Once exposed beyond localhost they are an availability risk (one client can exhaust them for everyone). Production must derive the real client IP from a trusted proxy (never from client-supplied forwarding headers) before those per-IP budgets are meaningful. S82 (code, 2026-10-24): under `APP_ENV=production` the client IP comes only from `CLIENT_IP_HEADER` (`x-real-ip` or `cf-connecting-ip`), requests without a valid value are refused (`503 CLIENT_IP_UNAVAILABLE`), the Better Auth ceilings key on it and guest bootstrap adds a `30/min` bucket per IPv4 address or IPv6 /64 under the global `600/min` (kept: it bounds anonymous guest rows; exhausting it now takes at least 20 distinct addresses; numbers documented in `src/modules/checkout/access.ts`). Still open: proving at S84/S88 that the chosen proxy overwrites a client-sent copy of that header (OD-9).

## Live adapter acceptance checklist (S156, 2026-11-02)

Every external adapter in 99ribu is a local sink or simulation today (for example `src/modules/advertising/meta/capi.ts` records `real_dispatch: no credentials, Graph request or Test Events evidence; local sink only`). Before the first real call to any provider (ads, shipping booking, payment, messaging), each row below needs an observed check on the final build and an owner who signs it. The rows come from the open and late-fixed findings of the AdsBookCMS audits (`~/Documents/work/research/99ribu-vs-adsbookcms-comparison-2026-11-02.md`); they are bug classes to test here, not claims that 99ribu has them.

| # | Check | Applies to |
|---|---|---|
| 1 | Every outbound request aborts after a configured limit (a test against a deliberately slow fake server proves it). | ads, shipping, payment, messaging |
| 2 | A timeout, 5xx or unreadable reply is recorded as `unknown`, never as rejected; an unknown outcome blocks a second send until resolved; an accepted request whose id was not saved is linked, not re-sent. | shipping booking, payment, ads |
| 3 | A cancelled, refunded or unpaid order emits no conversion and no Purchase, including a fresh-tab confirmation page. | ads |
| 4 | Adding credentials does not upload history: a configured start date gates the first upload. | Google offline conversions |
| 5 | The retry ladder is a pure function with unit tests: a dead token is terminal, a rate limit waits a flat period, other errors back off up to a cap; `event_time` stays the original time. | ads |
| 6 | A provider callback is stored as evidence and never moves order or payment state by itself. | payment |
| 7 | A superseded payment instruction keeps its provider id so a late payment on it can still be matched. | payment |
| 8 | A failing housekeeping step does not stop the others in the same scheduled run. | worker |
| 9 | Hot queries have an `EXPLAIN` and no full-table scan on the scheduled path. | worker, reporting |
| 10 | A status write is a guarded update (`where status in (…)`), not a write after an earlier read. | orders, payments |
| 11 | The phone normaliser maps `0062…`, `+62…`, `62…` and `08…` to one form. | checkout, messaging |
| 12 | Eligibility words are one vocabulary (no `paid` versus `settled` versus `success` drift). | ads, finance |
| 13 | Outbox liveness: retries are driven by the worker clock, not by visitor traffic. | worker |
| 14 | Admin screens do not call APIs their role may not use and swallow the 403. | console |
| 15 | No admin URL is placed in a message sent to a customer. | messaging |
| 16 | No page links to a route that returns 404 (the `UNBUILT_PAGES` and route-map tests already cover the console). | console, storefront |

Not covered by this list because it needs a decision first: per-courier COD fee, remittance days and volumetric divisor (read from the Mengantar documentation, never constants), and the legal and tax wording that needs an accountant or a lawyer.

## Runbook: DEC-033 one company warehouse in production (owner, after the deploy that carries it)

Order matters; every step is idempotent and audited. Run in the web container (`docker exec -it -w /app <web> ...`); `catalog`
steps ask for the owner's email, password and current code.

1. Off-host backup set (the deploy that carries 0059 already needs one).
2. `node scripts/catalog.ts rehome production` (dry run: warehouse to create, units to move, reserved units that stay) then
   `--apply` - creates `Gudang 99ribu, Surabaya` and moves every available unit into it by audited transfers. Reserved units
   (open orders) stay and ship from their origin. Rehome runs BEFORE import: publishing an offer needs complete stock in its
   default warehouse, so rebinding first would leave every product unpublishable until the stock arrives.
3. `node scripts/mengantar-areas.ts resolve-warehouses production` then `--apply` - sets the new warehouse's Mengantar area
   (Genteng); without it the warehouse has no live rates.
4. `node scripts/catalog.ts import production` - rebinds every importer-owned offer to the company warehouse and republishes
   (offers last edited by staff are reported as `preserved` and keep their warehouse: rebind them in Admin -> Produk).
5. Admin -> Produk -> Gudang -> Gudang 99ribu, Surabaya: pickup profile (street address, PIC name and phone) and
   "Terapkan kalender default" (fulfillment deadlines need a calendar), staff warehouse access for warehouse staff.
6. Check: checkout with one product shows "Dikirim dari Surabaya" and Mengantar couriers; `rehome production` dry run shows 0 to move.
   The supplier warehouses keep history; deactivate them later only when they hold no stock and no open order.

- After migrating, the worker starts deleting expired rows within a minute (500 per table per run per worker); first runs after a long backlog take several minutes to drain. Back up before the first production deploy that contains 0037 (runbook step 6), as always.

### Backups and restore drill (S85)

CODE implemented 2026-10-24 (`scripts/backup.ts`, `src/ops/backup.ts`); DEPLOY part not executed. One scheduled command writes one consistent **backup set** per run to `BACKUP_STORE` (`s3://bucket/prefix` on any S3-compatible endpoint, path-style SigV4; credentials only in Coolify env):

- `database.dump` — `pg_dump -Fc` under a snapshot exported in the same transaction that counts every table; `globals.sql` — `pg_dumpall --globals-only --no-role-passwords` (role passwords stay in Coolify env); `files.tar` — `catalog-media/` + `artifacts/` (regular files only, taken after the database snapshot so every referenced file is included); `auth-escrow.bin` — `BETTER_AUTH_SECRET` (32 bytes up to the key's OAEP limit, 318 bytes for RSA-3072) encrypted with the owner's RSA-OAEP-SHA256 public key (`BACKUP_ESCROW_PUBLIC_KEY`, ≥ 3072 bits); the server cannot decrypt it.
- `manifest.json`, uploaded last (a set without it is incomplete and never restored): SHA-256 and size of every object and of every archived file, per-table row counts, server version, auth secret fingerprint and escrow key id.
- This replaces the separate Coolify database backup + volume archive of the S85 row with one set whose parts share an instant; Coolify's own scheduled PostgreSQL backup can still be enabled as an additional copy. `BACKUP_DATABASE_URL` uses the database owner role (it must read every schema) and is set only on the worker, never on web; a dedicated read-only backup role is a possible S83 follow-up.
- Temporary files (dump, archive, decrypted secret held in memory only) go under `TMPDIR` (Node `os.tmpdir()`), default `/tmp`; point it at a private disk with room for one set (~55 MB today) if `/tmp` is small or shared.

**Integrity and authenticity — decision: no manifest signature; Object Lock + least-privilege credentials are a required DEPLOY precondition.** The manifest checksums detect corruption, truncation and a partial or edited object; they do not stop an attacker who can rewrite the whole set, manifest included. A signature would not either: the signing key would have to live on the server beside the bucket credentials, so whoever steals one steals both. What actually protects the sets is that the server can only add objects:
1. Server credentials (Coolify env): `PutObject` on the backup prefix only — no `GetObject`, no `DeleteObject`, no bucket-policy or lifecycle rights.
2. Bucket with versioning and, where the provider supports it, S3 Object Lock in compliance mode with a retention at least as long as the backup retention, so an existing version cannot be overwritten or deleted even with leaked credentials. Verify provider support at execution time; if Object Lock is unavailable, keep versioning plus a periodic owner-held copy outside that provider.
3. Retention by a bucket lifecycle rule (expire current versions after the retention window, noncurrent versions shortly after), not by `prune --apply`, which needs `DeleteObject`. `backup.ts prune` remains for `file://` stores and providers without lifecycle rules; run it only with operator-held delete credentials. Default policy (OD-5): 7 daily + 4 weekly, which `prune`'s `BACKUP_KEEP_DAILY`/`BACKUP_KEEP_WEEKLY` implement for those cases.
4. Uploads carry `Content-MD5`, `x-amz-checksum-sha256` (base64 of the manifest's SHA-256) and `x-amz-sdk-checksum-algorithm: SHA256`, all signed. The AWS PutObject reference (checked 2026-10-24) requires `Content-MD5` or `x-amz-sdk-checksum-algorithm` for uploads to an Object Lock bucket with a retention period, and S3 rejects a body that does not match `x-amz-checksum-sha256`. S3-compatible providers differ: `Content-MD5` is the long-standing, widely implemented check; the newer flexible-checksum headers may be ignored or, on a provider that does not know them, rejected. Verify one upload against the chosen provider (and its Object Lock support) before the first scheduled run; drop the flexible-checksum headers in `src/ops/backup.ts` if that provider refuses them.
5. Drill/restore credentials: read-only (`GetObject`, `ListBucket`), held by the operator, never on the server. The drill additionally proves authenticity of the content that matters: the escrow only opens with the owner's private key and its secret must decrypt the restored staff TOTP secrets.
- Escrow private key: generated and kept offline by the owner (`openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:3072 -out escrow.pem`; `openssl pkey -in escrow.pem -pubout` gives the public key for Coolify). Manual recovery without this repository: `openssl pkeyutl -decrypt -inkey escrow.pem -in auth-escrow.bin -pkeyopt rsa_padding_mode:oaep -pkeyopt rsa_oaep_md:sha256 -pkeyopt rsa_mgf1_md:sha256` (verified against the tool's output). Losing the key means a restored database locks every staff TOTP enrolment.

**Restore drill** (`node scripts/backup.ts drill <set-id|latest> --escrow-private-key <file>`), run from an operator machine or a disposable container with `RESTORE_ADMIN_URL` = superuser of a **disposable** PostgreSQL 18 server. It refuses, before any download or restore, when (a) `RESTORE_ADMIN_URL` has the same host:port as `BACKUP_DATABASE_URL`, (b) the restore server holds a database named `99ribu_production`, or (c) with `BACKUP_DATABASE_URL` set, both servers report the same `pg_control_system()` system identifier (same cluster under another name), or the identifier cannot be read. It then downloads and checksums the set, recovers the secret with the owner key and matches the fingerprint, extracts the archive into a temporary volume (manifest equality, every photo hashes to its name, `0600`/`0700`), restores into a new `99ribu_restore_<uuid>` with the S67 creating-XID reseal between data and post-data, then requires equal per-table row counts, zero unbalanced journals, the ledger immutability triggers, every referenced catalog photo present, every private artifact file referenced by an allowlisted file-key column present (`return_evidence.storage_key`, `shipping_label_artifact.storage_key`, `support_attachment.storage_key`, `affiliate_payout_evidence.artifact_id`; the `artifact_id` columns of `shipping_label_job`, `shipping_print_attempt` and `shipping_print_batch_item` are row references to `shipping_label_artifact`, not files), and every staff TOTP secret/backup-code set decrypting with the recovered secret (references are reported but not enforced for `test` sets, whose suites use temporary storage). It prints the DEC-005 catalog counts and elapsed time and drops the restore database and temporary files pass, fail or on `SIGTERM`/`SIGINT` (exit 143/130).

**Real restore** (damaged data only, never over the live database; owner-authorised): pick an **explicit set id**, never `latest` — the `backup` value printed by the last scheduled `create` run known to precede the damage (Coolify task log), confirmed present in `backup.ts list`, and recorded with the reason in this file; stop worker then web; run the drill on that id first; `node scripts/backup.ts extract <set-id> <new-dir>` with the same id and mount/copy it as the new volume (owner `10001`); on a fresh PostgreSQL resource run the S83 bootstrap (it creates `99ribu_production`; the finance write triggers require exactly that database name), `pg_restore --no-owner --role=99ribu_production_owner --section=pre-data --section=data`, apply the creating-XID reseal (`update app.<table> set created_xid = 'restored:' || created_xid` for every `app` table with that column), `--section=post-data`; put the escrowed `BETTER_AUTH_SECRET` back into Coolify env; point web/worker at the restored database; run the one-shot migrate service (a no-op for matching history that re-grants DML to the app role), then start web and worker. External effects after the backup instant are reconciled, not replayed.

Local evidence (2026-10-24, disposable databases only): `npm run test:integration -- --case=backup-restore` 5/5 (PASS drill, tampered object and wrong key refused, undecryptable TOTP fails, restore server holding `99ribu_production` refused, `SIGTERM` mid-drill drops the restore database); catalog-loaded local set (708 photos, 3,309 rows) drill PASS with 708/708 referenced photos and 14 categories / 49 origin warehouses / 368 `B99_` stock items / 392 `B99_*_OFFER` offers; production code path inside the built image against throwaway `postgres:18.6` containers over TCP (owner-role `pg_dump`, globals without superuser, owner role can read `pg_control_system()`): drill PASS in 10.7 s, and refusals for the live host:port, the same cluster under a second host name (system identifier) and a live server without `BACKUP_DATABASE_URL` (`99ribu_production` present).
