Production auth gates (open; local loopback profile only):

- 2FA brute-force budget: TOTP and backup-code verification are each budgeted `5/min` per account, keyed on the HMAC of the user id resolved from Better Auth's pending `two_factor` verification row (`src/modules/access/handler.ts`), so fresh sign-ins no longer reset it; unresolvable cookies share one conservative bucket. Residual: an attacker holding the password still gets up to `5` TOTP plus `5` backup-code guesses per minute per account, bounded further only by Better Auth's default two-factor account lockout (`10` consecutive failures -> `900s`, not separately load-tested here). Review these numbers against load evidence before exposure.
- Client IP: the sign-in ceiling (`300/min`, `src/modules/access/auth.ts`) and guest bootstrap ceiling (`600/min`, `src/modules/checkout/access.ts`) are global buckets because every request is stamped `127.0.0.1`. Once exposed beyond localhost they are an availability risk (one client can exhaust them for everyone). Production must derive the real client IP from a trusted proxy (never from client-supplied forwarding headers) before those per-IP budgets are meaningful.

### Backups and restore drill (S85)

CODE implemented 2026-10-24 (`scripts/backup.ts`, `src/ops/backup.ts`); DEPLOY part not executed. One scheduled command writes one consistent **backup set** per run to `BACKUP_STORE` (`s3://bucket/prefix` on any S3-compatible endpoint, path-style SigV4; credentials only in Coolify env):

- `database.dump` — `pg_dump -Fc` under a snapshot exported in the same transaction that counts every table; `globals.sql` — `pg_dumpall --globals-only --no-role-passwords` (role passwords stay in Coolify env); `files.tar` — `catalog-media/` + `artifacts/` (regular files only, taken after the database snapshot so every referenced file is included); `auth-escrow.bin` — `BETTER_AUTH_SECRET` (32 bytes up to the key's OAEP limit, 318 bytes for RSA-3072) encrypted with the owner's RSA-OAEP-SHA256 public key (`BACKUP_ESCROW_PUBLIC_KEY`, ≥ 3072 bits); the server cannot decrypt it.
- `manifest.json`, uploaded last (a set without it is incomplete and never restored): SHA-256 and size of every object and of every archived file, per-table row counts, server version, auth secret fingerprint and escrow key id.
- This replaces the separate Coolify database backup + volume archive of the S85 row with one set whose parts share an instant; Coolify's own scheduled PostgreSQL backup can still be enabled as an additional copy. `BACKUP_DATABASE_URL` uses the database owner role (it must read every schema) and is set only on the worker, never on web; a dedicated read-only backup role is a possible S83 follow-up.
- Temporary files (dump, archive, decrypted secret held in memory only) go under `TMPDIR` (Node `os.tmpdir()`), default `/tmp`; point it at a private disk with room for one set (~55 MB today) if `/tmp` is small or shared.

**Integrity and authenticity — decision: no manifest signature; Object Lock + least-privilege credentials are a required DEPLOY precondition.** The manifest checksums detect corruption, truncation and a partial or edited object; they do not stop an attacker who can rewrite the whole set, manifest included. A signature would not either: the signing key would have to live on the server beside the bucket credentials, so whoever steals one steals both. What actually protects the sets is that the server can only add objects:
1. Server credentials (Coolify env): `PutObject` on the backup prefix only — no `GetObject`, no `DeleteObject`, no bucket-policy or lifecycle rights.
2. Bucket with versioning and, where the provider supports it, S3 Object Lock in compliance mode with a retention at least as long as the backup retention, so an existing version cannot be overwritten or deleted even with leaked credentials. Verify provider support at execution time; if Object Lock is unavailable, keep versioning plus a periodic owner-held copy outside that provider.
3. Retention by a bucket lifecycle rule (expire current versions after the retention window, noncurrent versions shortly after), not by `prune --apply`, which needs `DeleteObject`. `backup.ts prune` remains for `file://` stores and providers without lifecycle rules; run it only with operator-held delete credentials. Default policy (OD-5): 7 daily + 4 weekly, which `prune`'s `BACKUP_KEEP_DAILY`/`BACKUP_KEEP_WEEKLY` implement for those cases.
4. Drill/restore credentials: read-only (`GetObject`, `ListBucket`), held by the operator, never on the server. The drill additionally proves authenticity of the content that matters: the escrow only opens with the owner's private key and its secret must decrypt the restored staff TOTP secrets.
- Escrow private key: generated and kept offline by the owner (`openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:3072 -out escrow.pem`; `openssl pkey -in escrow.pem -pubout` gives the public key for Coolify). Manual recovery without this repository: `openssl pkeyutl -decrypt -inkey escrow.pem -in auth-escrow.bin -pkeyopt rsa_padding_mode:oaep -pkeyopt rsa_oaep_md:sha256 -pkeyopt rsa_mgf1_md:sha256` (verified against the tool's output). Losing the key means a restored database locks every staff TOTP enrolment.

**Restore drill** (`node scripts/backup.ts drill <set-id|latest> --escrow-private-key <file>`), run from an operator machine or a disposable container with `RESTORE_ADMIN_URL` = superuser of a **disposable** PostgreSQL 18 server. It refuses, before any download or restore, when (a) `RESTORE_ADMIN_URL` has the same host:port as `BACKUP_DATABASE_URL`, (b) the restore server holds a database named `99ribu_production`, or (c) with `BACKUP_DATABASE_URL` set, both servers report the same `pg_control_system()` system identifier (same cluster under another name), or the identifier cannot be read. It then downloads and checksums the set, recovers the secret with the owner key and matches the fingerprint, extracts the archive into a temporary volume (manifest equality, every photo hashes to its name, `0600`/`0700`), restores into a new `99ribu_restore_<uuid>` with the S67 creating-XID reseal between data and post-data, then requires equal per-table row counts, zero unbalanced journals, the ledger immutability triggers, every referenced catalog photo present, every private artifact referenced by an `app.*.storage_key`/`artifact_id` column present, and every staff TOTP secret/backup-code set decrypting with the recovered secret (references are reported but not enforced for `test` sets, whose suites use temporary storage). It prints the DEC-005 catalog counts and elapsed time and drops the restore database and temporary files pass, fail or on `SIGTERM`/`SIGINT` (exit 143/130).

**Real restore** (damaged data only, never over the live database; owner-authorised): stop worker then web; run the drill on the chosen set first; `node scripts/backup.ts extract <set-id> <new-dir>` and mount/copy it as the new volume (owner `10001`); on a fresh PostgreSQL resource run the S83 bootstrap (it creates `99ribu_production`; the finance write triggers require exactly that database name), `pg_restore --no-owner --role=99ribu_production_owner --section=pre-data --section=data`, apply the creating-XID reseal (`update app.<table> set created_xid = 'restored:' || created_xid` for every `app` table with that column), `--section=post-data`; put the escrowed `BETTER_AUTH_SECRET` back into Coolify env; point web/worker at the restored database; start web (its migrate is a no-op and re-grants DML to the app role), then worker. External effects after the backup instant are reconciled, not replayed.

Local evidence (2026-10-24, disposable databases only): `npm run test:integration -- --case=backup-restore` 5/5 (PASS drill, tampered object and wrong key refused, undecryptable TOTP fails, restore server holding `99ribu_production` refused, `SIGTERM` mid-drill drops the restore database); catalog-loaded local set (708 photos, 3,309 rows) drill PASS with 708/708 referenced photos and 14 categories / 49 origin warehouses / 368 `B99_` stock items / 392 `B99_*_OFFER` offers; production code path inside the built image against throwaway `postgres:18.6` containers over TCP (owner-role `pg_dump`, globals without superuser, owner role can read `pg_control_system()`): drill PASS in 10.7 s, and refusals for the live host:port, the same cluster under a second host name (system identifier) and a live server without `BACKUP_DATABASE_URL` (`99ribu_production` present). Off-host S3 upload is verified only against an in-process signed test server and the AWS SigV4 reference vectors, not a real bucket; Object Lock/lifecycle are not configured anywhere yet.
