## Coverage and boundary
The draft covers catalog/categories/destinations, cart, checkout quotes, owned/guest orders, prepaid attempts, returns/private evidence, referral, affiliate balance/commission/payout views, beneficiary changes, warehouse stock/transfers/fulfillment, scoped admin order history/detail, versioned component HPP, derived finance summaries, return decisions/inspection, refunds, rates, shipping subsidy, financial reconciliation, staff grants, native website buyer/CS support chat and async operation recovery. Role/object validation is server-side; x-allowed-roles is documentation metadata, not enforcement.

No manual affiliate withdrawal endpoint: eligibility and queue allocation are automatic under PR-10, while finance transfers manually in the initial release. No buyer/affiliate route can set delivered_at, commission maturity, arbitrary refund/collect amounts or payout-success status. Only the protected staff evidence-verification operation may record a verified manual payment. No seller/tenant layer. Public product and category reads are intentionally unauthenticated. Guest order and cart capabilities are separate; parent/child identifiers must be validated together.

## Authentication proposal and gate
Browser sessions use a proposed HttpOnly Secure cookie transport; cookie name and Better Auth adapter settings are not selected by claiming a framework default. Stateful mutations require CSRF/origin controls. Native clients use a proposed short-lived bearer transport, not an assumed JWT format. Issuance, refresh, revocation, reauthentication proof and browser-to-app exchange are not invented here; freeze their protocol and routes in IAM before a native client can ship.

Guest cart/order capabilities are scoped credentials, sent through headers or a reviewed browser BFF/HttpOnly transport, never query strings or analytics. Token issuance/recovery is rate limited and uniform on unknown contacts. A referral cookie never grants order access. CORS allowlists, token lifetime/storage and allowed deep-link redirects are release gates. Do not put service/provider secrets in WebView or native binaries.

## Retry, conflict and money contract
Every proposed non-idempotent POST requires Idempotency-Key. Scope keys to authenticated actor or validated guest resource, plus operation; bind to normalized request hash. Same key/different body returns 409. Key retention must cover recovery windows and be fixed before release; original outcome lookup remains available. Concurrent calls serialize ownership of one logical effect. Queries use opaque cursor and bounded limit. Versioned operations reject stale state with 409.

Money is integer IDR. Totals, default/special commission rates and eligibility are calculated server-side. Quote selection creates a replacement immutable quote; stale quote/stock/subsidy requires buyer review. Split COD collections sum to parent total. Per-quantity exchange lineage resets only affected commission. Posted finance corrections append adjustments. Unknown provider outcomes remain unresolved until verified, not assumed failed or paid. Unexpected gateway errors may not follow Problem Details; clients must still recover safely.

## Owner-confirmed amendments — 2026-10-15

Product is a listing; Variant is the selected sellable offer. Each offer is exactly IDR99,000 and may be a unit, multipack, or bundle. A listing may expose different offer kinds together. `Variant.contents` identifies every physical stock component and included quantity; a quantity-two multipack is one offer purchase, not two charges. Bundle constituents have no arbitrary customer-facing individual price. Selection creates a cart line at the offer total; selecting another variant creates another IDR99,000 line. Physical inventory/movements/transfers now reference `stock_item_id`; warehouse pick rows link both purchased variant and physical component. Inventory-only components need no separate public listing. Server reservation must lock all components from one complete warehouse, including demand shared by other offers.

Packing means valid provider-issued waybill by H+2 from the immutable actionable purchase event: successful prepaid payment or confirmed COD, rather than initial unpaid order creation. Shipment booking can happen before the `packed` milestone; merely accepting a booking job does not count. `waybill_issued_at` and shipment linkage are server/provider sourced. Courier handover and actual buyer receipt are separate events; neither a staff packing call nor a waybill can mature commission. Replacement receipt resets H+10 for the affected purchased offer quantity while unrelated offer quantities remain independent. Bundle returns use the offer-level refund entitlement; replacing a defective component retains the original offer lineage and never invents a separately chargeable component price.

Eligible available commission at or above the effective server-configured threshold (**initial default IDR99,000 inclusive**) automatically creates a reserved finance queue entry after H+10 and applicable holds. Owner threshold changes are versioned under PR-20; the API response reports the effective value and grants no client-setting permission. Initial transfer is manual. Affiliate history reports queue/processing/unknown/verified success; it does not provide a withdrawal action. Finance uses `/admin/payouts`, an exclusive version-checked `/manual-transfer-claims` operation, private `/evidence-uploads`, then `/manual-transfer-verifications`. All are explicitly proposed first-party routes, not Virgo endpoints. The claim freezes server-calculated amount and verified beneficiary and supplies the private destination only to the reauthenticated active finance claimant. Bank transfer itself occurs outside this API. Unknown outcomes remain reserved until reviewed; expiry/retries must never initiate another transfer blindly. Verified evidence must match bank success, exact amount and frozen beneficiary, with bank-reference/evidence deduplication and atomic commission/ledger posting. No arbitrary client status or amount is accepted. Proof uploads are private, scanned, bounded and resource scoped; affiliate responses never include bank proof or private recipient details. Sensitive responses require no-store and no analytics/log exposure.

Manual finance exception/reassignment, proof retrieval and claim recovery interfaces still need their detailed screen/task contract before runtime implementation. The draft supplies core reservation/verification boundaries; it does not claim a complete finance console or executed bank transfer.

## Owner-approved admin controls — 2026-10-15

`owner` is the canonical role; **Super Admin** is its interface label. `/admin/orders` provides bounded cursor history, including completed, cancelled and refunded orders. `/admin/orders/{orderId}` adds typed order detail and cursor-paged lifecycle events. `orders.history.read` and object scope are mandatory: owner can inspect the business-wide history; explicitly authorized ecommerce, customer-service and finance staff require whole-order object access. Warehouse role cannot authorize whole-order history/detail, because order totals would disclose unrelated warehouse activity; warehouse history uses its existing scoped fulfillment/shipment views. Exact order/tracking reference and separate payment, fulfillment and return-state filters are bounded and combine with AND. Cursors bind filters and caller scope. These responses exclude customer contacts, private proofs and financial costs; a broader role alone never grants unrestricted PII. Sensitive reads are audited and served with `Cache-Control: no-store`.

`/admin/finance/summary` is read-only and derives gross merchandise, net merchandise revenue, recognized HPP, gross merchandise profit, estimated contribution, realized contribution, operating expenses/result, reconciled company cash, unsettled receivables, refund liability and affiliate liability independently. It returns report bounds, data `as_of`, cost policy version and completeness per metric. Missing HPP/fees produce an unknown/incomplete result rather than zero or an inflated complete profit. Period flows use `from` inclusive / `to` exclusive, with a maximum 366-day window; balances close at `to`. Contribution can be negative and is not company net profit: tax and overhead coverage must be explicit. Ledger recognition, historical snapshots, settlement and payout adjustments must preserve the finance specification. `hpp_basis` distinguishes actual lot costs, estimated snapshots, mixed and unknown costs. Inventory purchase cash flow must not be expensed again alongside recognized COGS, and affiliate payout settles a liability without recording affiliate expense twice. Operating result is not finalized net profit while tax or cost coverage is incomplete. Detailed expense posting/allocation and period-close APIs remain explicit T-12 implementation scope; this summary does not claim a complete ERP.

`/admin/stock-items/{stockItemId}/cost-versions` reads bounded immutable HPP history and appends a version using integer IDR per physical component, nullable unknown cost, safe source reference, reason, effective timestamp and optimistic `expected_version`. Zero is the expected initial version; successors compare against the current version. Backdated application before server acceptance is rejected; corrections append, while order snapshots and posted history remain unchanged. Offer HPP follows purchased component quantities. Fixed IDR99,000 offer pricing remains enforced, and profit is never a writable field. Physical stock continues through existing version-checked stock movements/transfers rather than arbitrary balance overwrites.

Financial endpoints require owner or an explicit finance permission (`finance.summary.read`, `finance.costs.read`, `finance.costs.write`); `ecommerce_admin` and warehouse roles receive no financial cost access by default. Cost writes require actor-scoped idempotency and audit evidence. Permission metadata describes the intended contract; runtime grant evaluation, finance formulas, temporal cost selection, object authorization and concurrency remain implementation obligations.

## Native website customer-service chat — PR-22, 2026-10-15

Website chat is a first-party buyer-to-CS conversation. `/support/conversations` creates and lists owned conversations; scoped detail, message history/POST, read markers, private image uploads/downloads and event replay live below that resource. Authenticated buyers use their session; guests require an opaque HttpOnly server-bound support session. A phone/order number, cart or referral cookie never grants conversation/order access. Optional product context must be published; order context requires verified authenticated ownership or an exact-order guest proof. Messages and attachments never authorize payment, refund, payout or order-state changes. No external messaging provider or automatic bot is claimed.

Message text is plain text up to 4,000 characters, with up to three validated private JPEG/PNG/WebP images of at most 5 MiB each. Require nonblank text or at least one ready attachment. Enforce actual upload bytes, decoded-image limits, MIME checks, malware scanning, re-encoding/EXIF removal, conversation ownership and quotas. Metadata polling reports pending/ready/rejected scan state; image bytes require the same scoped authorization and ready state. There are no arbitrary remote image URLs or credential-bearing redirects; authorized image bytes return directly. CS attachment use requires an active assigned claim and explicit CS role.

POST messages require both HTTP `Idempotency-Key` and durable `client_message_id` deduplication bound to actor/conversation/body. Stable conversation-local public sequence is assigned only after atomic persistence; duplicate retries never duplicate a message. A new buyer message atomically reopens resolved/waiting conversations. Cursor history is authoritative. `/events` proposes authenticated SSE reads plus bounded JSON cursor replay, with scoped opaque cursors, authorization on reconnect and expired-cursor recovery. Browser credentials use same-origin HttpOnly cookies, never stream query parameters. Stream delivery, reconnect and read acknowledgements are independent of financial/delivery status.

CS inbox/claims/assignments/status/messages/events/internal notes/read markers use `/admin/support/...` with canonical `customer_service` or `owner` roles. Inbox assignment filters distinguish unassigned, assigned-to-me and all authorized conversations. Atomic version-checked claims prevent concurrent ownership. Sending a reply requires the current active claim to belong to the sender; owner takeover first uses an audited version-checked reassignment. Status is open/waiting_customer/resolved. CS operations cannot silently impersonate another claimant. `/admin/support/conversations/{conversationId}/events` provides separately authorized CS SSE/JSON resume using the same public event projection; guest support sessions cannot enter this route. Notes remain privately polled; inbox queue may use bounded polling.

Internal notes have separate storage identifiers and staff-only schemas/routes; never expose them in buyer messages/history/event replay, notification content, public conversation timestamps, public sequence gaps or unread counters. Public read markers explicitly identify `reader_side` customer/staff without personal identity. Customer-visible staff acknowledgement is the maximum actual acknowledged read among permitted CS participants. Staff inbox unread uses that current agent's private last-read marker, never the team aggregate. Read updates are monotonic, bounded by the highest authorized public sequence, and never mark the other side as read.

Before T-24/T-25 implementation, freeze guest session bootstrap/rotation/expiry/recovery, safe native/browser transport issuance, authenticated stream expiry/reconnect, event retention/resync, attachment retention and notification policy. These are explicit implementation gates, not claims of an already operating chat service.
