# S177 — Checkout voucher codes (stage 2)

Status: brief only (owner request 2026-11-05: "siapkan tahap 1 voucher dan brief tahap 2 termasuk kecamatan tujuan dan metode pengiriman"). Stage 1 (the hidden checkout UI) is built locally behind a constant that is off. `TASKS.md` row S177 owns scope and gates; `STATUS.md` owns state. This brief never overrides the row.

## Goal

A buyer types a code in checkout ("Punya kode voucher?"), sees the discount before ordering, and the order freezes exactly that discount. Staff create and stop codes in the admin. Codes can be limited by destination kecamatan, shipping method (courier service), payment method, minimum purchase, period, quota and per-buyer use.

## Recommendation: a voucher is a code-gated promotion

99ribu already has a shipping-promotion engine (`src/modules/promotions/`, tables `app.promotion*`). It has versioned configuration with audit reason, a budget reserved at order creation and committed or released later (`reservations.ts`), a per-buyer counter (`promotion_buyer_usage`, keyed by the quote's `customer_key`), payment-method, region (`prov-*`, `quotes.ts:28`) and service filters, exclusive/allowed stacking with priority, deterministic per-parcel allocation (`allocation.ts`), and unit-level cancellation splits. Building a second engine for vouchers would duplicate every one of those money paths.

Extend it instead:

1. **Code gate.** A promotion gets an optional unique `code` (normalised: NFKC, trim, upper-case, `^[A-Z0-9-]{3,32}$`). A promotion with a code applies only when the quote carries that code; one without a code keeps applying automatically as today.
2. **Kecamatan targeting.** Add district regions next to provinces: `dist-<province>-<city>-<district>` built from the chosen `app.shipping_area` row with the same normaliser as `provinceRegion`. A shipment carries both its `prov-*` and `dist-*` ids, so a rule may target provinces, kecamatan or both. The admin picks kecamatan through the same catalogue search the checkout uses (`searchDistricts`).
3. **Shipping-method targeting.** Already present as `service_ids` (courier service keys from the rate plan). The admin lists the courier services seen in Mengantar estimates.
4. **Benefit kinds.** Today a rule only subsidises shipping (`fixed` or `percentage`, capped per order). Add a `target` of `shipping` (current behaviour) or `merchandise`. A merchandise discount is allocated across order lines in proportion to line totals with the same largest-remainder method, so returns and refunds can split it per unit like the existing subsidy split. Owner decides whether stage 2 ships both or shipping only (see decisions).
5. **Checkout flow.** "Pakai" calls a quote recompute with the code (no separate apply endpoint holding state). The quote document freezes `voucher: {code, promotion_id, version_id, amount, target}` with the plan; order creation re-validates in the same transaction that reserves the budget and the per-buyer counter (`reservePromotions`), so two buyers cannot both take the last quota. Any change (address, courier, payment method, cart) recomputes and may drop the voucher with a reason.
6. **Reason codes.** The backend returns one of `NOT_FOUND`, `NOT_STARTED`, `EXPIRED`, `EXHAUSTED`, `PER_BUYER_LIMIT`, `MIN_SUBTOTAL`, `METHOD_NOT_ELIGIBLE`, `DESTINATION_NOT_ELIGIBLE`, `SHIPPING_METHOD_NOT_ELIGIBLE`, `STACKING_CONFLICT`. Stage 1 already maps each one to Indonesian copy. To limit code guessing, an inactive or unknown code both answer `NOT_FOUND`, and the apply path has its own rate limit per client.

## Money rules that must hold

- DEC-025: each offer's price stays its own frozen whole-rupiah price ≤ Rp99.000. A voucher is an order-level discount line, never a change to the offer price.
- Totals: `amount_due = merchandise + shipping − shipping subsidy − merchandise discount + payment fee (DEC-029, when the buyer bears it)`, never below zero, every part frozen on the order.
- COD: the per-parcel COD amount uses the post-discount parcel share.
- Payment-fee basis (DEC-029 QRIS 0.7 %): computed on the amount actually charged after the discount.
- Who bears the discount (store or platform) is posted as an immutable money movement like the shipping subsidy; affiliate commission base needs an owner decision.
- Returns and cancellations: release or reverse the voucher share per unit; a fully cancelled order releases the reservation and the buyer's usage.

## Owner decisions (needed before code)

1. Kinds in this slice: shipping discount only, merchandise discount only, or both?
2. Allowed with COD, or prepaid only by default?
3. Who bears the cost: store, platform, or set per voucher?
4. Stacking with automatic shipping promotions: never, or allowed per voucher?
5. One voucher per order (recommended) or several?
6. Per-buyer identity for guests: normalised WhatsApp number (recommended, it is the quote `customer_key`) or account only?
7. Affiliate commission computed before or after the merchandise discount?
8. Single shared codes only, or also generated single-use code batches (e.g. birthday vouchers, S127)?
