## Goal

Exercise 99ribu's real AutoLaris HTTP client end to end against a loopback stand-in: list channels, create a payment instruction, read advice, survive timeouts and replays. The simulator (`simulatedAutolaris`, database-backed, with timeout faults) stays the proof for paid-state and money postings; this slice adds the **wire** layer it cannot cover.

## Evidence

- The seam is `AutolarisClient` (`src/modules/payments/autolaris.ts:19`: `listPayment`, `createPayment`, `advice`, each with an optional `AbortSignal`). `autolarisClientFor(target, sql, options)` returns `simulatedAutolaris` for local or test and throws `503 AUTOLARIS_LIVE_GATED` otherwise. `paymentAdapter(sql, target, faults, autolaris?)` (`worker.ts:8`) already accepts an injected client.
- `src/modules/payments/autolaris-live.ts` (67 lines) is **not wired anywhere** and only `tests/autolaris-live.test.ts` imports it. It requires an https origin (`:27`), an `AUTOLARIS_API_KEY` of 8–512 printable characters, sends `Authorization: Bearer <key>`, `redirect: "error"`, a 10 s timeout, and calls `GET /api/h2h/list_payment`, `POST /api/h2h/create_payment`, `POST /api/h2h/advice`.
- `parseCreatePayment` requires `rc 00`, `trx_id` matching `^[A-Za-z0-9_-]{1,64}$` and exactly one non-empty instruction field (`virtual_account`, `qr`, `payment_code`, `url`).
- `dispatchAutolarisPayment` checks `listPayment` first, sends `reff_id = 99R + attempt id without dashes` (same attempt, same value), refuses when the provider `amount` or `total` differs from the requested amount, and leaves `responded_at` null on a timeout so reconciliation replays the same create.
- Advice polling: every 300 s, at most 24 polls, final read at order expiry; the job takes `payment:<attemptId>` advisory lock and `lockPaymentOrder`, writes `app.autolaris_observation`, and settles only through `settleLocalOperation` and `registerProviderEvent`.
- `classifyAdvice` settles only on `rc 00` + `data.status PAID` + a positive safe-integer `data.amount` (`SIMULATED_SETTLEMENT` placeholder). The callback route (`/api/v1/payments/autolaris/callbacks`) stores the raw body with a SHA-256 and **never changes payment state**; no signature or source check exists ("contract unpublished").
- The stand-in serves `list_payment`, `submit`, `advice` and dev levers; it does not serve `create_payment`, ignores `reff_id`, has no failures, and answers advice with `ket PAID, data {awb}`.
- Official docs: `create_payment` request has `reff_id, channel_code, customer_id, customer_name, customer_phone, customer_email, expired (YYYYMMDDHHMMSS), amount, callback_url`; the success sample shows `total = amount + admin`. 99ribu requires `total == amount`. The docs also say never to call `create_payment` after `submit` for the same checkout.

## Recommendation

1. **Loopback client factory.** Add a reader (next to `readAutolarisLiveConfig`, not inside it) that accepts only the S163 `providerOrigin` with the literal bearer `local`; it must not weaken the https rule of the live reader. `autolarisClientFor` returns `liveAutolaris(thatConfig)` only when `providerOrigin` is set on a non-production target; otherwise today's behaviour (simulator, or `AUTOLARIS_LIVE_GATED`).
2. **Keep money proof on the simulator.** Settlement, postings, expiry and receipts are already proven there. Against the stand-in, assert only the wire layer: channel list parse, create parse, `reff_id` replay, amount/total check, timeout handling, advice pending.
3. **Settlement against the stand-in stays labelled unproven.** If S171 makes the stand-in answer the exact `SIMULATED_SETTLEMENT` shape, it is an invented contract: tests may use it to drive the settle path once, but no document, comment or UI may call it real. S97 closes it.
4. **Do not copy AdsBookCMS's retry.** It marks a timed-out create `failed` and retries with a **new** `reff_id`, which can double-bill. 99ribu keeps the same `reff_id` and reconciles by advice.
5. **Fee conflict (A2).** The docs' sample adds the fee on top; 99ribu refuses when `total != amount`. Do not reconcile this against the stand-in; make the stand-in's `fee_mode` configurable (it exists in AdsBookCMS's simulator) so both behaviours are testable, and leave the product decision to S97 or the owner.
6. **Egress.** Wrap the loopback client's `fetch` so any URL outside `providerOrigin` throws; keep `redirect: "error"`, the 10 s timeout and sanitised errors (no URL, no body, no key).

## Scope

In: the loopback config reader, the factory branch, tests against an in-test fake and (in S169) the real stand-in, the egress guard.
Out: the callback route (unchanged, still no state change), real settlement mapping, fee policy changes, UI copy (S168).

## Allowed and protected paths

Allowed: `src/modules/payments/**`, `src/config/**` (read, one accessor), `tests/integration/autolaris-*.test.ts`, `tests/autolaris-live.test.ts`, `scripts/check-tests.ts`. Protected: `migrations/**`, `src/db/**`, `src/modules/finance/**` except reading, journals and postings.

## Test plan

- Create: instruction field parse (exactly one of four), bad `trx_id`, `rc != 00`, two instruction fields, over-long field, missing channel in `list_payment` refuses.
- `reff_id`: same attempt replays the same value; a stand-in that dedupes returns the same `trx_id`; one that does not is a **documented stand-in gap**, not a 99ribu pass.
- Timeout before and after the provider answers (stand-in levers from S171): no second payment reference is created, the operation stays `pending`, reconciliation replays the same create.
- Amount and total mismatch refuse; `fee_mode` both ways.
- Advice: `rc 02` pending; unknown shapes classify `unknown`, never `settled`; a settled answer settles exactly once and posts once (reuse the simulator's posting assertions); a replayed advice is a no-op.
- Egress: any request not to `providerOrigin` fails the test; mode off keeps `AUTOLARIS_LIVE_GATED` in production.
- `--case=autolaris-payments`, `PR-5`, `PR-8`-style money cases still PASS.

## Risks and escalation

- R4: money path. A real separate-agent review bound to the final surface is required; self-review is invalid.
- Invented contract: stand-in settlement shape must not leak into `classifyAdvice`. Do not edit `SIMULATED_SETTLEMENT` to match the stand-in.
- The simulator and the stand-in are two sources of truth for payment state; the stand-in must never write 99ribu's database.
- Escalate on any change that touches postings, the settle path or the callback route.

## Done when (runnable)

`npm run test:integration -- --case=autolaris-payments` and `--case=PR-5` PASS including the new wire cases; the egress test fails a stray host and passes the loopback one; the paid-once and posted-once assertions pass on the simulator path; R4 review recorded.
