## Goal

One registered, repeatable acceptance case proves the whole provider-backed local journey against the **real stand-in**, including the failure paths, and proves nothing leaves loopback. It also re-proves S68 because checkout code changed.

## Evidence

- Cases are registered in `scripts/check-tests.ts`: add the selector to `validSelectors` (~line 51), to `integrationOnlySelectors` only if the case is integration-only, add a branch in the file-mapping ternary (from ~line 65), and add a row to the README acceptance command registry (columns: command, required state, executed scope). `--case=all-current` reads every `tests/<mode>/*.test.ts`.
- The runner fails on skipped, TODO or empty tests and on cancelled results, runs files in process isolation, serially, with a 30-second per-test timeout (`checkFiles`, `scripts/check-tests.ts:6-39`). It is not concurrency-safe; local and test databases are fixed (`99ribu_local`, `99ribu_test`) with `current_database()` checks.
- Browser cases run against the app at `127.0.0.1:3099` and need `PLAYWRIGHT_CHROMIUM_EXECUTABLE`; `T-31` is the model (`tests/browser/storefront-checkout.test.ts` plus the label test).
- The stand-in keeps state in memory and cannot take port `0` from the environment (S167): the case must probe a free port and pass `DEV_PROVIDERS_PORT`.

## Recommendation

1. **Integration file** `tests/integration/local-providers.test.ts`: spawn the stand-in (`npm run dev:providers` in `~/Projects/adsbookcms`) on a probed free port, wait for `GET /`, run the journey and the negatives of S164–S166 against it, tear it down in `after`. The test **fails, never skips,** if the repository, the command or the port is unavailable.
2. **Browser file** `tests/browser/local-providers.test.ts`: guest journey from search to an order with a payment instruction in the 390 and 1440 viewports; each S168 state reached through a stand-in lever (S171).
3. **Egress guard test:** wrap `globalThis.fetch` for the process under test and fail on any URL whose origin is not the configured stand-in (and not the app itself).
4. Register `--case=local-providers` for both modes, add the README registry row (required state: stand-in running, mode variable set, local catalogue loaded) and record in the evidence the stand-in `HEAD` hash from S167.
5. After the case passes, re-run `--case=T-23`, `PR-3`, `PR-4`, `PR-5`, `T-31` and the S68 acceptance because checkout code changed; a material change reopens those checks and their downstream consumers (AGENTS.md freshness rule).

## Scope

In: the two test files, the registry entries, the egress guard, evidence.
Out: product code (fix in the owning slice), changes to the stand-in (S171), production anything.

## Allowed and protected paths

Allowed: `tests/integration/local-providers.test.ts`, `tests/browser/local-providers.test.ts`, `scripts/check-tests.ts`, `README.md`, `package.json` (only if a unit file is listed). Protected: `src/**`, `migrations/**`.

## Test plan (what the case asserts)

- Guest: search area by name and postal code, get couriers, choose COD and a prepaid channel, create the order, receive an instruction, advice pending, order expiry path.
- Negatives: timeout, 5xx, malformed body, no route, COD unsupported, forged or stale destination id, duplicate `reff_id`, amount mismatch.
- Money: paid exactly once and posted exactly once on the simulator path; no second payment reference after a timeout.
- Guard: any request outside loopback fails the case; with the stand-in down the case **fails**.

## Risks and escalation

- Flaky in-memory state: each run starts its own instance on its own port.
- Time: the full case may take minutes; keep per-test timeouts explicit and do not raise the runner's global one.
- Escalate if a product defect found here needs a change outside the slices S163–S168; open it as a finding instead of patching in the test slice.

## Done when (runnable)

`PLAYWRIGHT_CHROMIUM_EXECUTABLE=/usr/bin/google-chrome npm run test:integration -- --case=local-providers` and `npm run test:browser -- --case=local-providers` PASS with the stand-in available and FAIL without it; the regression set (`T-23`, `PR-3`, `PR-4`, `PR-5`, `T-31`, S68 acceptance) is green on the final surface; `check-boundary` PASS; STATUS and BUILD-LOG record commands and results.
