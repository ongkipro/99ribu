## Goal

Prove that the S95 adapter, now pointed at the stand-in (S164), behaves correctly on every branch a real provider can produce: couriers, COD flags, timeouts, malformed bodies, expiry and cache. S164 switches the path; S165 proves the behaviours and settles the courier-key mismatch.

## Evidence

- `parseEstimate` (`mengantar.ts:25`) keeps a courier only if `courier in COURIERS` (`:18`, case-sensitive), hides `unsupported === true` and `unsupportedOriginSpx === true`, requires a positive safe-integer `price`, and sets COD only when `unsupported_cod === false` and `coverage_cod !== false` (a missing flag means no COD).
- The stand-in's courier keys `J&T`, `IDexpress`, `Anteraja`, `Paxel` are not in `COURIERS`; they would be hidden. Real keys are `JT`, `iDexpress`, `anteraja` (observed 2026-07-19 per the local docs).
- `estimateRates` (`rates.ts:47-65`): timer `min(2000, remaining)` and abort; at most 100 rates, exact keys, `source === adapter.source`, integer `shipping_amount >= 0`, unique ids, `expires_at > request.now`; any non-`AccessError` becomes `503 SHIPPING_RATE_UNAVAILABLE`; a bad shape `503 SHIPPING_RATE_INVALID`; expiry `409 SHIPPING_RATE_EXPIRED`; `503 SHIPPING_RATE_TIMEOUT`. `buildShippingPlans` shares one 3000 ms deadline.
- Plan building sorts by price and ignores COD-unsupported rates for COD orders, answering `422 COD_UNAVAILABLE` or `422 NO_SUPPORTED_ROUTE` when nothing works.
- The stand-in has no delay or fault lever, ignores `courier`, never sets `unsupported`, always gives an ETD, and its `codFee` is 3 % of `COD_AMOUNT` only when that parameter is sent (the real COD fee semantics are not modelled).

## Recommendation

1. **Fix courier keys in the stand-in (S171)** so the real keys are served (`JT`, `iDexpress`, `anteraja`, plus `unsupported` and `unsupported_cod` cases). Do not add stand-in names to 99ribu's `COURIERS` map: that would teach production code about a fake.
2. Cover every branch with the **in-test HTTP fake** from S164 (deterministic, no cross-repo dependency) and keep the real stand-in for S169's end-to-end journey.
3. Do not change `estimateRates`, its limits or its error codes. If a behaviour looks wrong, record it as a finding for the owner; production parity is the point.
4. Confirm whether 99ribu sends `COD_AMOUNT` to the estimate (the research did not settle it). If not, COD fee display must stay a 99ribu-side number, never the stand-in's.

## Test plan

| Case | Expectation |
|---|---|
| keyed answer with real courier keys | each courier becomes a rate with whole-rupiah price; ids stable |
| `unsupported: true` / `unsupportedOriginSpx: true` | courier hidden |
| `unsupported_cod: true` (or flag missing) | COD hidden; COD order with only such routes: `COD_UNAVAILABLE` |
| non-positive or fractional price | courier dropped |
| answer slower than 2000 ms | `SHIPPING_RATE_TIMEOUT`, no quote, draft kept |
| 5xx, non-JSON, empty object, more than 100 rates | `SHIPPING_RATE_UNAVAILABLE` / `SHIPPING_RATE_INVALID`, no quote |
| replay of the same estimate within 5 min | one provider call (cache) |
| quote older than its expiry at order creation | `SHIPPING_RATE_EXPIRED` |
| 301st fetch in a minute | provider budget refuses; the buyer sees the retry state |
| mode off | `PR-3` and `PR-4` unchanged |

Reset the in-process cache between cases (`resetMengantarRates()`).

## Risks and escalation

- The stand-in's fake prices must never be asserted as real tariffs; assert structure and invariants, not amounts, except where the fake is deterministic and the test says so.
- The 2000 ms cap versus the adapter's 5000 ms fetch timeout: the effective limit is 2000 ms; note it in the evidence so no one "fixes" it.
- Escalate if parity requires changing money behaviour.
